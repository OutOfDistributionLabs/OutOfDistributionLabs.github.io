# Reusable engine benchmarking process

Out of Distribution Labs · Version 1 · October 7, 2026

Use this programme for any decision-support engine added to an agent harness. A planning document is not a completed experiment. The research publishing runner updates public progress and ntfy; the sentinel described here determines scientific readiness. They have separate responsibilities.

Depth levels: **2 focused**, **3 substantial**, **4 deep**, **5 very deep**. They indicate review/engineering intensity, not fixed durations. Break deep stages into separate checkpoints and repeat sentinel checks after material changes. A “sentinel” is an explicit evidence review, not an assumed independent agent or a model silently judging its own success.

## Stages, substeps and gates

| Stage | Depth | Substeps and required artifacts | Sentinel: advance criteria | Redo/stop conditions |
|---|---:|---|---|---|
| 01 Scope | 3 | 1.1 Define user decision/problem; 1.2 specify intervention and target population; 1.3 separate mechanism/task/efficiency claims; 1.4 state falsifiers; 1.5 map mechanism to concrete decisions; 1.6 define an acceptable reliability/cost criterion and audit the best reported benchmark entries with version, date, settings and primary-source snapshots. Artifact: scope and hypothesis map. | Measurable outcomes; no assumed advantage; claims bounded to population; theory maps to intervention; a claimed frontier gap is evidenced against an explicit criterion, not assumed. | Vague “intelligence” claims → rewrite scope. |
| 02 Benchmark qualification | 4 | 2.1 Audit primary sources; 2.2 acquire and pin data/scorer/images; 2.3 audit license and information boundary; 2.4 map task/repository overlaps; 2.5 run evaluator-only reference and malformed-patch checks; 2.6 measure resource feasibility; 2.7 audit failure mechanisms on a separate development sample before committing to a richer intervention. Artifact: qualification report + frozen source manifest. | Stable assets; correct official scoring; agent view excludes answers; feasible resource envelope; split contamination documented. | Missing raw corpus, scorer failure or leaking gold → repair adapter or replace benchmark before tuning. |
| 03 Experimental design | 5 | 3.1 Define primary estimand and endpoint; 3.2 native/strong flat/full arms; 3.3 match information and aggregate budgets; 3.4 pairing, split and ordering; 3.5 failure policy; 3.6 analysis and practical thresholds; 3.7 rough power and expenditure estimate. Artifact: draft preregistration. | One primary claim; equal ceilings; indexing control; explicit uncertainty/multiplicity; no confirmatory labels inspected. | Confounds or underpower → redesign/estimation study; do not invent evidence. |
| 04 Engine specification | 4 | 4.1 Select minimal useful decision; 4.2 evidence-grounded entities/edges; 4.3 revision invalidation; 4.4 tool input/output schema; 4.5 observed coverage and safe fallback; 4.6 cost and ablation contract. Artifact: versioned specification. | B/C same API/data cap; no oracle labels; stable citations; useful testable intervention; honest uncertainty. | Unverifiable summaries or incomparable flat tool → revise schema/design. |
| 05 Engine implementation | 5 | 5.1 deterministic parser/index; 5.2 multi-view graph; 5.3 rank/broaden policy; 5.4 revision/evidence tracking; 5.5 official SDK MCP server; 5.6 separate client smoke tests; 5.7 bounded path access and negative cases; 5.8 ablation switches. Artifact: packaged server, tests, fixtures. | Actual initialize/list-tools/call-tool round trip; schema validation; stale references rejected; no answer access; flat baseline works; language coverage matches study. | Server-only demonstration, guessed coverage truth or parser failures → redo implementation. |
| 06 Harness and observability | 5 | 6.1 isolate fresh CLI sessions; 6.2 model/version/prompt locks; 6.3 MCP client configuration; 6.4 costs/cache accounting; 6.5 sandbox/evaluator separation; 6.6 immutable trace and patch capture; 6.7 replay tests; 6.8 unique scorer IDs. Artifact: adapters and accounting audit. | Agent actually calls MCP; independent arm state; trace captures all spend including engine; hidden tests inaccessible; common result schema. | Interactive-memory carryover, unknown spend or cache collision → repair instrumentation. |
| 07 Development pilot | 5 | 7.1 repository-stratified small development set; 7.2 interleaved A/B/C sessions; 7.3 independently grade; 7.4 inspect failures and leakage probes; 7.5 tune only on development; 7.6 repeat after fixes; 7.7 rubric reviewer trial. Artifact: raw pilot traces + diagnostic report. | Reliable execution; no leakage; scorer stable; consultation/overhead measured; all tuning recorded. Improvement is not required. | Infra instability → redo; ineffective but functioning engine → revise thesis or continue as negative-result study. |
| 08 Confirmatory freeze | 4 | 8.1 pilot-based discordance/power simulation; 8.2 untouched confirmation manifest; 8.3 numeric caps/pricing; 8.4 hash model/engine/scorer/config; 8.5 analysis script fixtures; 8.6 stopping rule and protocol registration. Artifact: immutable preregistration + hashes. | All locks filled; plausible precision/power or explicitly estimation-only; holdout untouched; no discretionary stopping. | Missing budget/version/sample → hold. Changed engine → new development cycle/freeze. |
| 09 Confirmatory execution | 5 | 9.1 randomized blocked schedule; 9.2 fixed budget paired runs; 9.3 track failures/dropouts; 9.4 seal patches before independent grading; 9.5 schema and completeness audit; 9.6 compute locked primary analysis. Artifact: all outcomes, traces, costs, analysis. | Planned tasks accounted for; symmetric retry policy; valid pairing; no outcome-based omissions; scorer/analysis unchanged. | Infrastructure-invalid results → rerun prespecified affected units; scientific null → report, not redo until significant. |
| 10 Mechanism and robustness | 4 | 10.1 C/B comparisons; 10.2 token-matched graph/coverage/admission ablations; 10.3 cold/warm accounting; 10.4 uncertainty/stale-state stress tests; 10.5 blinded trace review; 10.6 repository sensitivity. Artifact: mechanism and robustness report. | Fixed secondary family; all variants/costs reported; oracle arms labelled; independent labels for calibration. | Winning subgroup selected after results → exploratory, not new primary conclusion. |
| 11 Cross-harness / scale replication | 5 | 11.1 adapter conformance for Claude Code, Antigravity, etc.; 11.2 independently paired within-harness arms; 11.3 same model where supported; 11.4 if not, report model×harness bundles; 11.5 later fixed-aggregate-budget multi-agent factorial. Artifact: per-harness replication and interactions. | Versions fixed; actual MCP calls logged; cost/sandbox parity; within-harness effects reported; scaling claims measured directly. | Interface mismatch → adjust adapter; differing models → no pure harness ranking. |
| 12 Report and reproduce | 4 | 12.1 full outcome table including nulls; 12.2 claim/evidence audit; 12.3 sanitized traces/configs; 12.4 independent reproduction attempt; 12.5 limitations/next thesis; 12.6 public progress/report and notifications. Artifact: reproducibility bundle + report. | Results support exact claims; qualifications retained; protocols/deviations public; no secrets; reproducible scorer invocation. | Unsupported claim → narrow; irreproducible results → repair/reclassify, not hide. |

## Mandatory sentinel record after every stage

Record: stage ID; disposition `advance`, `redo` or `stop`; reviewer identity/role; independence status; date; each criterion with pass/fail and evidence citation; artifact SHA256s; prior-stage evidence-record digest; limitations; remediation and the next allowed action. A review should distinguish machine-checked properties from human judgments. An author may perform the first review, but it must be labelled self-review. An independent review is needed before strong public claims; unavailable reviewers do not become fictional agents.

`tools/benchmarking/methodology.py` validates a project protocol, prints the stage plan, calculates rough power, emits a randomized paired run plan from a frozen manifest, and records sequential sentinel decisions. It enforces required attestations and file hashes, not scientific truth. It does not execute models, manufacture trials, or implement MCP. Use results/schema/adapter tests in later engineering stages.

For `redo`: identify the smallest failed substep and redo it with a new artifact version. If upstream artifacts change, hash verification blocks later advancement until affected reviews are renewed; start a new review ledger for the revised protocol, retaining the old ledger in history. For `stop`: preserve evidence and explain why. For a negative effect: complete the analysis/report or formulate a separately registered follow-up; never repeatedly redo the confirmatory experiment in search of significance.

## Publish and repeat

Create `research/PROJECT` with the general publisher. Link to a protocol, benchmark audit, contract, manifest and sentinel history. Checkpoint every material substep and sentinel; independently configured page/ntfy heartbeats indicate activity only (new defaults: 60-second page updates and 300-second notifications). Keep experiment outputs out of public progress until sanitised, and publish methodology and all deviations. When planning ends, stop that heartbeat. Implementation resumes as a distinct project or a deliberately versioned longer programme; never mark unexecuted stages complete.
